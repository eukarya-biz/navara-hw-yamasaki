# 新宿・子ども目線迷子体験 — 地下街シーン

PLATEAU の新宿区地下街モデル(LOD4)を、子どもの目線の高さで歩き回るシーン。

## 起動

**必要なもの**: Node.js 18以上(Vite 5の要件。`node --version` で確認)。

以下をターミナルにそのまま貼り付ければ、クローンから起動まで一気に進む:

```bash
git clone https://github.com/eukarya-biz/navara-hw-yamasaki.git
cd navara-hw-yamasaki
npm install
npm run dev
```

ターミナルに表示された `http://localhost:5173/` をブラウザで開く。「はじめる」を押すと開始。
画面をクリックするとマウスで視点が回る(Esc で解除)。W/S で前進・後退、A/D で回転、Shiftで走る。

`git` が無い場合は、リポジトリ右上の **Code > Download ZIP** から取得し、
展開したフォルダで `cd` してから上記の `npm install` 以降を実行すればよい。

**公開版**: [https://eukarya-biz.github.io/navara-hw-yamasaki/](https://eukarya-biz.github.io/navara-hw-yamasaki/) (ローカル起動が不要な場合はこちら)

## このシーンの前提

`PersonViewPlugin` 0.0.2 には**重力もコリジョンも無い**。垂直方向の処理は
`alt += dirZ * altSpeed * dt` を `[minAlt, maxAlt]` でクランプするだけで、
床を検出する処理は存在しない。デフォルトの `altSpeed` は 30 m/s なので、
高さ約 3 m の通路では下降キーを 0.33 秒押しただけでデータの外に出てしまう。

そこで、tileset の glb ジオメトリから床と天井を実測してグリッド化し
(`public/data/ubld_walkgrid.json`)、それを使って**床追従と壁の当たり判定を
自前で実装**している。実装は `src/walkgrid.ts`。

地表(globe)は地下から見上げると不透明な蓋になるため、`view.globe.hideUnderground`
を有効にしている。建物・地形・航空写真のレイヤーは一切読み込まない。

## データの実測値

glb の頂点を測地座標に戻し、各タイルの `boundingVolume.region` と突き合わせて
**平均誤差 0.00** を確認したうえでの数値。glTF は Y-up、3D Tiles は Z-up なので
`(x, -z, y)` の軸変換が必須(これを忘れると高さが約 80 m ずれる)。

| 項目 | 値 |
|---|---|
| 範囲 | 緯度 35.690633..35.695045 / 経度 139.697650..139.703828 |
| 高さ | 15.32..45.49 m(標高・東京湾平均海面基準) |
| 三角形 | 133,714(うち水平に近い面 55,804) |
| 歩行可能セル | 7,127(2 m 格子 = 28,508 m²) |
| 主要フロア | 25.0 m(1,784 セル)/ 33.5 m(1,332)/ 30.5 m(834)/ 30.0 m(671)/ 24.0 m(584) |
| 開始地点から到達可能 | 全セルの 99.8%、最長経路 702 m、標高 15〜39 m |


確認できていない。見た目(明るさ、SSAO の効き、色)は実機での調整が必要。

## グリッドの再生成

地下街データを差し替えたときは、`tools/build_walkgrid.py` を実行して
`public/data/ubld_walkgrid.json` を作り直す。

```bash
pip install pygltflib numpy
python3 tools/build_walkgrid.py
```

## GitHub Pagesでの公開

`vite.config.ts` で `base: "./"` を指定し、データの参照パスも全て相対にしてある。
**リポジトリ名に依存しない**ので、名前が決まっていなくてもそのまま公開できる。

### なぜ相対にする必要があるか

GitHub Pagesのプロジェクトサイトは `https://<org>.github.io/<repo>/` で配信される。
ルート絶対パス(`/data/...`)のままだと、`new URL()` の解決でリポジトリ名が落ちる:

| ページURL | `/data/...`(修正前) | `data/...`(修正後) |
|---|---|---|
| `.../navara-shinjuku/` | `github.io/data/...` **404** | `github.io/navara-shinjuku/data/...` OK |
| `localhost:5173/` | `localhost:5173/data/...` OK | `localhost:5173/data/...` OK |

**localhostでは両方成功する**ので、ローカル検証では絶対に気づけない。
以前2日かけた「tileset.jsonのURL解決」と同じ罠の別バージョン。

検証済み: `dist/` をサブディレクトリに置いて配信し、tileset.json・walkgrid.json・.glb の
全てがマジックバイト付きで届くこと(HTMLフォールバックでないこと)を確認した。

### 公開の手順

`.github/workflows/deploy.yml` を同梱してある。mainにpushするとビルドしてPagesに配信する
(型チェックと `npm test` も通す)。ビルド成果物をコミットする必要はない。

情シスへの依頼内容: **Settings > Pages で「Source: GitHub Actions」を有効化**。
eukarya-bizではリポジトリ作成者がPagesを有効化できないため、この1手だけ依頼が必要。

### 提出前チェック

- `.gitignore` あり(`node_modules` / `dist` / `.env` 系を除外)
- APIキー・認証情報のハードコードなし(検索して確認済み)
- 外部通信はPLATEAUの属性表示リンク1本のみ。データは全て同梱で自己完結
- `public/data/` は**除外していない**(これが無いとシーンが読めない)

## 公式テンプレートとの構成差(2026-07-30 調査)

`reearth/navara-template` を実際にクローンして比較した結果:

| | このプロジェクト | 公式テンプレート |
|---|---|---|
| navaramap系 | 0.0.2 | **0.0.4** |
| パッケージ名 | アンダースコア (`three_plugins`) | **ハイフン** (`three-plugins`) |
| three | 0.183.2 | 0.184.0(`@types/three` も0.184.0で一致) |
| vite | 5.4.20 に固定 | **8.0.8** |
| パッケージマネージャ | npm | **pnpm** |
| `vite.config.ts` | 必要(WASM除外+アセット静的コピー) | **存在しない** |

**課題文の「NPMにはまだ公開されていないのでテンプレートをクローンして使え」は古い記述**で、
テンプレート自身がnpmから入れている。構成上の違反は無い。

要検証(⑤フィードバックに書く前に確認すべき):
- テンプレートは `vite.config.ts` なしで `addDefaultPhotorealScene()` と `view.atmosphere` を
  使えている。**0.0.4で修正されたのか、pnpmのnode_modules構造(シンボリックリンクで平坦化しない)
  が `import.meta.url` の解決を正しくしているのか**は切り分けが必要
- 「vite 8が動かない」の症状(`Cannot find module 'rollup'` の芋づる欠落)は
  **npmのoptional dependenciesの既知バグの典型**。テンプレートはvite 8.0.8をpnpmで動かしている。
  vite 8の非互換と結論づけるのは早い
- 「ハイフン版は0.0.0のプレースホルダ」は0.0.2時点の話。**0.0.4ではハイフン版が本体**

### 公式ドキュメントがテンプレートに同梱されている

`.claude/skills/navara-usage/` に454行のリファレンス(`custom-desc.md` /
`declarative-api.md` / `low-level-api.md` / `plugins.md` / `recipes.md`)。
`.d.ts` から手探りする前にここを読むべきだった。

照合の結果、**このプロジェクトのカスタム記述子の作法は公式と一致していた**:
- 基底クラスは `id`/`visible` しか保持しないので `config` は自分で持つ ← 一致
- `view.registerMesh(key, Class)` → `view.addMesh<T>({ key: {...} })` ← 一致
- `position` はECEFメートル、または `matrixWorld` + ENUフレーム ← 一致

**未活用だと分かったAPI**:
- **`InstancedMeshDesc`**(0.0.2に存在) — `add`/`removeAt`/`updateAt`/`clear`/`replaceAll`/`count`
  でインスタンス管理ができる公式の基底クラス。群衆の大量描画はこれを使う
- **`OverlayPlugin`** — ワールド座標→スクリーン座標のDOMオーバーレイ。
  `setPositions()` / `onUpdate(({projected}) => ...)`。方向ヒントやマーカーに使える
- `getPassKey()` — メッシュがどのシーン/パスで描かれるかを選べる
- `view.pickDepthPosition(x, y)` — ピクセル下のECEF位置

**安定性の注意**: `Plugin` と `ViewContext` は Tier 1 APIで、マイナーバージョン間で
壊れる可能性がある(`ThreeView` は Tier 0 で安定)。カスタム記述子のコンストラクタは
`ViewContext` を受け取るので、この結合は認識しておく必要がある。

## ゴール(親との再会)

実装は `src/goal.ts` と `src/audio.ts`。

**ゴール地点は実測**(勘ではない)。STARTから歩行グリッドを幅優先探索して到達可能な
7,656状態のうち、「最も高い床 かつ 開けている かつ STARTから遠い」条件で選定:

| 項目 | 値 |
|---|---|
| 座標 | 緯度 35.6910744 / 経度 139.7011900 |
| 床 / 天井 | 38.50 m / 41.13 m(頭上2.63m) |
| 開放度 | 周囲25セル中14セルが歩行可能 |
| STARTからの距離 | 189ステップ = **378 m** |

データ上の最高床は39.21mだが、そちらは狭い(開放度12/25・頭上1.91m)ので、
「立って待っている場所」として見栄えのする38.5m層を選んだ。

`goaltest.mjs` がこの座標を `src/goal.ts` から読み出して歩行グリッドと突き合わせる
(床が実在するか・STARTから到達可能か・接近地点が親と同じ階層か)。`npm test` に含めてある。

### 誘導は「光」

企画の核が「迷う不安」なので、常時表示の矢印は不安を消してしまう。代わりに
**親の真上から差す光の筋**を置いた。視線が通ったときだけ見えるので、通路では
迷ったままで、曲がり角で光が見えた瞬間が希望になる。

デフォルト記述子にはポイントライトが無い(ambient / sun / probe のみ)ため、
光は**加算合成の発光ジオメトリ**で作っている。むしろトーンマッピングで
潰れないので、遠くから見えるビーコンとしてはこちらの方が確実。

保険として、デバッグパネルに「方向ヒントを出す」(矢印)トグルを用意した。**既定はOFF**。

### 再会の演出

親から3.5m以内に入ると発火し、1.8秒かけて環境光を3倍・露出を1.45倍まで持ち上げ、
そのあとベースより明るい値(環境光2倍・露出1.2倍)に落ち着く。安心感は持続させたいので
元の暗さには戻さない。あわせて「みつけた」の表示と、あれば `relief.mp3` を再生。

親は7秒周期で±50°ゆっくり見回す。親も探している、という含みと、彫像に見えないため。

### ハマった点(記録)

デバッグ用「親のそばへ移動」の着地点を、当初 `GOAL.lat - 0.00007` と式で出していたが、
**そのセルは33.5mの床しか持っておらず**、飛ぶと床追従で5m下の別階層に落ちて再会できなかった。
グリッドを検索して親と同じ38.5m層にある実在セルを `GOAL_APPROACH` として定義し直した。
**座標をオフセット計算で作ると階層をまたぐ**ので、必ずグリッドで裏を取ること。

### 群衆のざわめき(合成・素材不要)

`public/audio/ambience.mp3` があればそれをループする。**無ければ合成する**ので、
素材ゼロでも音は鳴る。

**最初の実装は「波打ち際」に聞こえた。**理由は明確で、
**フィルタしたピンクノイズ + ゆっくりした振幅変化は、砕ける波そのもの**だから。
人混みと波を分ける要素が3つとも欠けていた:

| | 波 | 人混み |
|---|---|---|
| 振幅変化の周期 | 2〜8秒(うねり) | **4〜6Hz(音節の速さ)** |
| 立ち上がり | ゆるい | **速い(20〜35ms)** |
| ピッチ | 無い | **ある(声帯の基本周波数)** |

旧実装の変調は220〜540ms周期に250msのスムージングで、完全に「うねり」側だった。

**作り直した方式**: ノイズは静かな部屋鳴りだけに落とし、群衆本体は
**短いピッチのある発話を大量に重ねて**作る:

- **のこぎり波**を成人の基本周波数(男声85〜155Hz / 女声165〜255Hz)で鳴らす。
  ピッチがあることが「人の声に聞こえる」ことのほぼ全て
- **母音のフォルマント**(日本語の あいうえお のF1/F2)のバンドパス2本を**並列**に通す。
  直列にすると2本目が1本目をほぼ打ち消して何も残らない
- **1音節130〜270ms、立ち上がり20〜35ms**。これで振幅変化が音節の帯域に入る
- 抑揚として基本周波数を±8%グライドさせる(固定すると機械音になる)
- **発話の間隔を不規則にする**(等間隔だと機関銃になる)
- 全体にローパス2.6kHz(遠くの雑踏に高域は残らない)

**発話頻度は人数に連動**して毎秒4〜26回。1音節0.2秒なので同時発音は最大7程度で、
個々の声を聞き分けられないマッシュになる。

合成の旧メモ(参考):
- **ピンクノイズ**をベースにする(Paul KellettのIIR近似)。
  ホワイトノイズだと「サー」という静電気の音になる。人の声の帯域は低域寄りなので、
  1/f に近い重み付けにするだけで「部屋の音」に近づく
- **母音のフォルマント帯**(280 / 760 / 1900 Hz)のバンドパスを3層通す。
  これでノイズが「声」に寄る
- **数百msごとに各層のゲインとフォルマントをランダムに歩かせる**。
  群衆は一定ではなく個々の会話が起き伏せするので、これが「ざわめき」を作る。
  固定するとただの「ブーン」になる
- 3層は再生レートを変えて位相が揃わないようにし、左右に振り分ける
- 通路の反響用ディレイにも少し送る

**音量は実際に近くにいる人数に連動する**(`sim.visibleCount()`)。
背景で一定に鳴らすのではなく、狭い通路では静かになり開けた場所で満ちる。
この差が「人混みに入っていく」感覚を作る。

終幕でカメラが700m上空へ離れるときは4秒でフェードアウトする。

**注意**: 合成なので、本物の駅のざわめきには及ばない。より良くするなら
FreesoundのCC0の雑踏録音を `ambience.mp3` として置けば自動的にそちらが使われる
(雑踏は言語に依存しないので、日本語の声より素材が見つけやすい)。

## 歩いた軌跡と、始点・終点のマーカー(`src/trail.ts`)

俯瞰ショットで「この広さ」を見せたうえに、**実際に歩いた経路**を重ねる。
迷った回数・引き返した場所・行き止まりが全部線に残るので、
「広い」だけでなく「どう迷ったか」が見える締めになる。

- **記録は距離基準**(1.5m間隔)。時間基準にすると立ち止まっている間に点が溜まる。
  25m以上飛んだ場合はテレポート(デバッグボタン・階層ジャンプ)として扱い、線を繋がない
- **リボンは板ポリゴンで作る。`THREE.Line` は使わない。**
  WebGLの多くの実装で線幅が無視されるので、ポリラインだと距離に関係なく1pxの髪の毛になる。
  ワールド単位で幅を持たせるには面を張るしかない。幅4.5m = 697m上空で約9.7px
- **階段でもリボンは水平を保つ**(進行方向を水平に潰してから外積を取る)。
  これをしないと坂でリボンが捻れる
- マーカーは高さ130mのビーム(青=開始地点 / 黄=親を見つけた場所)。
  **歩行中は出さない。**3mの通路の中に130mの光の柱が立つのは絵として破綻するし、
  そもそも「常時表示の矢印は不安を消す」という設計判断に反する

### 実機で「軌跡が見えない」問題(解決済み)

ビームは見えるのに軌跡だけ見えなかった。原因は**構造物の中に埋まっていた**こと。

軌跡は床+0.5mに置いているが、**地下街の天井は最高45.4m**まである。
697m上空から見ると天井が上から蓋をするので、内側の線は完全に隠れる。
ビームは高さ130mで天井を貫くので見えていた、という非対称だった。

**対策**: 軌跡とマーカーは `depthTest: false` + `renderOrder` を上げて、
深度に関係なく最後に描く。これは「シーン内の物体」ではなく
**地図に重ねるデータ**なので、隠れない方が正しい。

### 歩かずに確認する方法

`grid.pathBetween()` で歩行グリッド上の最短経路を実際に探索できるようにした。
デバッグパネルの「**見本の軌跡で再生(歩かずに確認)**」で、
STARTからゴールまでの本物の経路(190セル = 約380m、標高24.9〜37.8mで階層をまたぐ)を
軌跡として流し込んでから演出を再生する。直線ではなく実際に歩ける経路。

サンプル数が5未満のときは警告を出すようにした
(テレポートで飛ぶと軌跡がほぼ無くなり、原因が分かりにくいため)。

### float32の制約(群衆と同じ理由)

`BufferGeometry` の座標も**float32**。ECEFは約400万mなので、
生のECEFで経路を組むと目に見えて折れ・揺れが出る。
リボンもビームもアンカー1点からのローカル座標(メートル)で組み、
オブジェクト側のtransformでECEFに載せている。

### 検証

`trailtest.mjs` でジオメトリを算術的に検証している(見た目では壊れに気づきにくいため):
直線での幅が正確か / 階段でリボンが水平か / 直角のカーブで潰れないか /
同一点が連続してもNaNにならないか / インデックスが頂点数を超えないか /
上空から何ピクセルで見えるか。

## 導入と終幕(`src/framing.ts`)

これが無いと、作品は「灰色の通路を歩けるデモ」に見えてしまう。自分が4歳で、
つないでいた手が離れて、誰かが探している——という前提が画面のどこにも無いため。

- **導入**: 4行の設定 + 操作説明 + 「はじめる」ボタン。
  迷子の体験の前に長文を読ませるのは自己矛盾なので、意図的に短くしてある
- **終幕**: カメラが上昇して地下街の全体を見せたあと、探した時間・歩いた距離と、
  この場所の実測サイズ(歩ける床の面積・最長経路)を出す。
  「この広さで手が離れると、子どもの視界は1メートルに戻る」という締め。
  背景を薄いグラデーションにして、俯瞰の絵がテキストの後ろに残るようにしてある
  (伝えたいのが**広さ**なので、画面を覆ってしまうと台無しになる)

### 終幕のカメラ(20秒・旋回)

再会したら、データ全体を俯瞰する位置まで上昇しながら**120°旋回**する20秒のショット。
上昇は前半45%で終わり、旋回は最後まで続くので、登りきったあとも絵が変化し続ける。

**高度は固定値ではなく計算で出す。**最初は165m固定にしていたが、実機で端が切れた。
測ってみたら当然で:

| | 値 |
|---|---|
| データ範囲 | 南北 474 m / 東西 502 m / **対角 690 m** |
| 中心 | 35.6928566 / 139.7008250 |
| 165mで画面に収まる幅(FOV50・真下) | **154 m** ← 全体の1/4以下 |
| 必要な距離(FOV50・余白15%) | **851 m**(高度697m / 水平488m) |

`grid.bounds()` で範囲を実測し、`view.camera.raw` から**実際のFOVとアスペクト比を読んで**
必要な距離を毎回計算している。ウィンドウの形が変わっても収まる。

カメラはデータ中心を軸にした円錐面上を回り、常に中心を向く
(円周上の点から中心への方位は、その点の角度+180°)。

`Esc` か `Space` でスキップできる。デバッグパネルの「終幕のカメラ」で
長さ・回る角度・見下ろす角度・余白を実機で調整でき、
「ここから再生」で親を探さずに確認できる。

### ゴール後のカメラ上昇でハマった点

**`teleport({ alt: 200 })` では上昇できない。**PersonViewPluginのtickが
入力の有無に関係なく**毎フレーム**高度をクランプする:

```js
x = Math.max(minAlt, Math.min(maxAlt, currentHeight + input))
```

`maxAlt` は `range.max + 4` ≈ 43mなので、200mへteleportしても次フレームで43mに戻る。
`teleport()` 自体はクランプしないので一瞬だけ上がって落ちる、という分かりにくい挙動になる。

**回避策**: カメラ高度は `クランプ後の高度 + fpvHeightOffset` で、
**`setFpvHeightOffset()` はクランプされない**。なので上昇はオフセットを伸ばして行う。
プレイヤーの論理位置は床に残るので、俯瞰の画が立っていた場所の真上に固定されるという
副作用もちょうど良い。

デバッグパネルの「上空200mから俯瞰」も同じバグを持っていたので直した。

**globeも透明にする必要がある**。地表シェルは地上のカメラと地下街の間で
不透明な蓋になる(`view.globe.transparent = true` / `opacity = 0`)。

上昇中は頭の上下動とマウスルックの両方を止める(どちらも同じ値を書きに来るため)。
上昇後は `pitch` を到達値に同期させて、マウスを動かした瞬間に水平へ戻らないようにしている。

### 導入ボタンのもう一つの役割

ブラウザは**ユーザー操作なしにAudioContextを開始できない**。以前はこれを
「キャンバスをクリックしてポインタロック」に相乗りさせていたが、
本来無関係な操作なので、「はじめる」ボタンに移した。

`personView.start()` も導入を閉じるまで遅延させている。プラグインの `state` は
`start()` ではなく `init()` で初期化されるので(実装を確認済み)、
導入表示中にフレームループが `getState()` を呼んでも安全。

## 歩きの感触

**速度1.9 m/s。これはリアリズムではない。**3〜4歳の実測は時速1.5〜2km
(0.42〜0.56 m/s)で、それだと378mの道のりが**11〜15分**になる。
以前の1.4 m/sは既に大人の歩行速度だったので、「リアルにする」と3倍遅くなる。
根拠は物語側に置いた——**焦った子どもは急ぐ**。

**「子どもらしさ」を作っているのは速度ではなく歩調。**4歳児の歩幅は30〜35cm
(大人は約70cm)なので、同じ距離で頭の上下動が倍近く起きる。
`setFpvHeightOffset()` を毎フレーム動かして再現している。

| | 値 | 含意する歩幅 |
|---|---|---|
| 既定 | 4.8 歩/秒・振幅1.8cm | 40 cm |
| 最初の実装 | 2.9 歩/秒 | **66 cm(ほぼ大人・失敗)** |

最初は2.9 Hzにしていたが、`feeltest.mjs` が「歩幅66cm = 大人の歩容」だと検出した。
**自分の書いたコメントと実装が矛盾していた**ので、テストで気づけたのが大きい。
以降このテストが歩幅45cm未満を保証する。

振幅は歩調を上げたぶん小さくした(速い上下動を大きな振幅でやると、足音ではなく
振動に見える)。感触は画面を見ないと判断できないので、デバッグパネルの
「歩きの感触」で歩調・振幅・ON/OFFを実機で詰められるようにしてある。

歩いていないときは位相をリセットして基準の高さに戻す(止まった瞬間に
中途半端な高さで固まらないため)。

## 群衆(インスタンシング版)

実装は `src/crowd-instanced.ts`。旧版(`src/crowd.ts`、1人=6メッシュ)は親モデルの
人型ビルダーを提供するために残してある。

### なぜ書き直したか

旧版は1人あたり6メッシュ = **6ドローコール**だったので、25人で150。
三角形数ではなく**ドローコールが天井**で、人数を増やせなかった。

インスタンシング版は**部位ごとに1つのInstancedMesh**にまとめる。胴体は全員で1ドローコール、
頭も1つ、という具合に**合計6ドローコールで固定**。人数に依存しない。

| 人数 | 旧版 | インスタンシング版 |
|---|---|---|
| 25 | 150 | 6 |
| 240 | 1,440 | 6 |
| 600 | 3,600 | 6 |

腕脚のアニメーションは維持している(インスタンスごとに行列を持つので、ポーズを共有しない)。

### 設計を決めた制約: `instanceMatrix` はfloat32

これが全ての設計理由。実測(`matrixtest.mjs`):

```
ECEF x  -3955318.2       -> float32  -3955318.25   (誤差 0.05 m)
同じ x + 2cm             -> float32  -3955318.25   (完全に同一!)
```

静的な0.05mの誤差はまだ我慢できる。**問題は2行目**。2cmは1.2m/sで歩く1フレーム分の距離で、
この桁のfloat32では**表現できない**。つまりECEFを直接インスタンス行列に入れると、
群衆は**一切動かない**(位置が約5cm格子に量子化され、歩くのではなく飛ぶ)。

対策として **InstancedMesh本体をアンカー1点に置き**(こちらはオブジェクトの
transformなのでfloat64)、**各インスタンス行列はアンカーからのローカル
オフセット(メートル)**にした。137mのローカル値なら誤差は5e-6 m。

これがAPIの「Local position relative to the parent group」の意味だと思われる。

### フレームの規約

アンカーはNorth-Up-Eastフレームなので、ローカル `(x, y, z)` = `(北 m, 上 m, 東 m)`。
モデルの正面は`+Z`、左右は`±X`。だから**ローカルX軸まわりの回転が手脚の前後スイング**になる。

`matrixtest.mjs` で検証済み:
- 方位0/90/180/270°で、モデル正面が実際に北/東/南/西を向く
- 脚のスイングで**股関節の位置が動かない**(`-0.090, 0.750, 0.000` で固定)、
  足はZ(前後)に動きX(左右)には動かない

### 密度: 全体に散らすのは失敗だった

最初は歩行グリッド7,127セル全体に散らしたが、実機で「スカスカ」になった。測ったら明白:

| | 値 |
|---|---|
| 全体の歩行可能面積 | 28,508 m² |
| 240人での密度 | **0.0084 人/m²**(1人あたり119 m²) |
| 視界50m内の歩行可能面積(START) | 2,656 m² |
| 全体に散らして0.15人/m²にするなら | **4,276人**必要 |

全体に散らすと**約9割が見えない場所に立っている**ので無駄になる。

**対策: プレイヤー周辺(`localRadiusM`、既定60m)に集めて、外に出た人を使い回す。**
`recycle()` がPersonオブジェクトを再利用して近くの歩行可能セルに移すので、
アロケーションもインスタンス番号の付け替えも起きない。視界(`visibleM` = 50m)の
外側で入れ替わるので、画面内に人が湧いて見えることもない。

既定500人で、視界内の密度は約0.13人/m²(「やや混雑」0.15の少し手前)。
HUDに「群衆 N/M 表示中」を出したので、実機で見ながらスライダー(0〜1500)で調整できる。

参考値: 0.15=やや混雑 / 0.3=混雑 / 0.6=ラッシュ

### LODと配置
- 60m超(`localRadiusM`): 使い回して近くに再配置
- 50m超: シミュレーション自体をスキップし、スケール0に潰して非表示
  (インスタンスに可視フラグは無いため)。これが大半なので、ここが効いている
- 22m超: 体は動くが手脚のスイングは止める
- 22m以内: フルアニメーション

既定は500人。デバッグパネルのスライダーで0〜1500まで変更可能。

**毎フレームの床判定は `surfacesAt()` を使う**。当初 `cellsWithin(lat,lng,1)` を
使っていたが、これは最大25個のセルオブジェクトの配列を毎回生成するので、
数百人規模だと毎フレーム数千個のアロケーションになる。`surfacesAt()` は
生の配列を返すだけなので確保が起きない。

### 色

`getInstanceColor` が用意されているが、位置ベースで割り当てたいので
`createMesh()` で `setColorAt` を使っている。`MeshStandardMaterial` は
NavaraがG-buffer書き込み用にパッチするShaderLibマテリアルの一つなので、
**SSAOが群衆にも効く**(追加作業なし)。

## 群衆(試作・アセット不使用)

外部キャラクターパックを使わず、コードだけで生成した群衆。実装は `src/crowd.ts`。

- 見た目: Three.js の Box ジオメトリだけで組んだ簡易な人型(胴体・頭・腕2・脚2)。
  Kenney/Kay Lousbergパックの代わり。色をキャラごとに変えて「コピペ感」を軽減。
- 動き: `ubld_walkgrid.json` から現在地周辺の歩行可能セルをランダムに選び、
  そこへ歩いていく → 到着後に一時停止 → 別のセルへ、を繰り返す(無秩序に歩く)。
  壁の中や柱の中に湧かない。
- アニメーション: 脚・腕をサイン波で振るだけの簡易ウォークサイクル(ボーン無し)。
- LOD: プレイヤーからの距離でアニメーション更新と表示/非表示を間引く
  (`lodAnimateM`/`lodVisibleM`、既定 20m/45m)。
- デバッグパネルの「群衆(試作)」フォルダで人数変更・再配置が可能。

**検証したこと**: `tsc --noEmit` の型チェック、`vite build` の本番ビルド、
歩行グリッドの空間クエリと徘徊ロジックを実データに対して 2000 ステップ分
シミュレーション(NaN無し、常に歩行可能セル上、移動距離も妥当)。

**検証していないこと**: 描画そのもの(ヘッドレスブラウザ未入手のため)。
特に以下の2点は理屈の上では正しいはずだが実機で最初に確認すべき箇所:
1. `geodeticToVector3` への `lat`/`lng` は「ラジアン」という型定義のコメントを
   信じて変換して渡している。もし全員が原点付近など明後日の位置に出るなら、
   度(degree)のまま渡す方に変えてみること(1行の修正で済む)。
2. 進行方向(heading)からキャラの向きを求める式(`src/crowd.ts` 末尾のコメント参照)。
   もし脚の振りと進んでいる方向がズレて見えるなら、符号を反転してみること
   — 位置・床追従のロジックとは独立しているので、ここだけ直せばよい。
